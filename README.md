# Orders & Products

Приложение для учёта приходов и продуктов по тестовому заданию. Основные экраны повторяют структуру предоставленных макетов: список приходов, панель выбранного прихода, подтверждение удаления и продукты с фильтром по типу.

## Что можно проверить

- Открыть приход рядом со списком, посмотреть связанные продукты и закрыть панель.
- Сравнить количество продуктов и суммы в USD и UAH. Валюты суммируются отдельно, пересчёта по курсу нет.
- Добавить приход и продукт, проверить ошибки формы, отменить или подтвердить удаление. Вместе с приходом удаляются его продукты и цены.
- Отфильтровать продукты одним select по типу. Выбор сохраняется после перезагрузки. Поиск работает по названию, а на странице продуктов — ещё и по серийному номеру.
- Открыть вторую вкладку: счётчик изменится в обеих. Изменения инвентаря также передаются остальным вкладкам.
- Переключить русский и английский интерфейс, открыть аналитику и загрузить интерактивную карту.
- Установить PWA в поддерживаемом браузере. Без сети открывается отдельная страница; данные инвентаря в offline-кеш не попадают.

Демонстрационные записи синтетические. Цены не являются рыночными предложениями, точки на карте обозначают примеры мест хранения.

## Запуск в Docker

Нужны Docker с Compose и Node.js 24 для генерации локального ключа. Вся среда приложения и MySQL описана в `compose.yaml`.

Из каталога проекта:

```sh
JWT_SECRET="$(node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))')" \
  docker compose --env-file .env.example up --build
```

После сообщения `[server] listening on port 3000` откройте [http://localhost:3000](http://localhost:3000). Локальный демонстрационный вход: **demo / demo-inventory**. Команда создаёт схему и начальные записи. Сгенерированный ключ действует только для этого запуска.

Остановка из другого терминала:

```sh
docker compose --env-file .env.example down
```

Данные сохраняются в Docker volume. Повторный запуск не перезаписывает существующий инвентарь. Для полного сброса именно локальной демонстрационной базы добавьте `--volumes` к команде остановки.

## Разработка без контейнера приложения

Нужны Node.js **24.7+ в ветке 24**, npm и MySQL 8.4. Базу можно оставить в Docker:

```sh
npm ci
docker compose --env-file .env.example up -d --wait db
cp .env.example .env
```

В локальном `.env` задайте:

```dotenv
APP_ORIGIN=http://localhost:3000
DATABASE_URL=mysql://inventory:inventory-local@127.0.0.1:3307/inventory
DEMO_USERNAME=demo
DEMO_PASSWORD=demo-inventory
ALLOW_DEMO_SEED=1
```

Отдельно задайте `JWT_SECRET`: не меньше 32 случайных байт. Команда для генерации значения:

```sh
node -e 'console.log(require("node:crypto").randomBytes(32).toString("hex"))'
```

Затем создайте схему, демоданные и запустите приложение:

```sh
node --env-file=.env scripts/migrate.ts
node --env-file=.env scripts/seed.ts
npm run dev
```

`APP_ORIGIN` должен совпадать с адресом в браузере, включая протокол и порт. Для этого примера используйте `localhost`. Настоящий `.env` не добавляется в Git.

Production-режим Node.js запускается командами `npm run build` и `npm start`. Нужен постоянный процесс: Socket.io работает на том же HTTP-сервере, что и Next.js.

## Проверки

Быстрый проход без базы и браузера:

```sh
npm run verify
```

Команда генерирует типы маршрутов, проверяет TypeScript, ESLint, unit-тесты и production-сборку. `typecheck`, `lint`, `test` и `build` доступны отдельно.

Полная локальная проверка:

```sh
npm run qa
```

Для неё нужны работающий локальный Docker Engine и установленный Google Chrome. Скрипт поднимает отдельный MySQL `inventory_test` в памяти, запускает интеграционные тесты и приложение на `127.0.0.1:5173`, затем Playwright. Он проверяет пользовательские сценарии, API, SSR, JWT, Socket.io, PWA и страницы на ширинах **1440 / 1024 / 768 / 390 / 360**. После проверки сервер, браузеры и тестовая БД останавливаются. Отчёты, трассы и скриншоты находятся в `.qa/` и не попадают в Git.

Порты 3308 и 5173 должны быть свободны. QA запускается из чистого каталога проекта без настоящих `.env`-файлов: у тестового окружения собственные демонстрационные настройки. Обычная база `inventory` не используется.

Отдельный интеграционный прогон требует запущенного `test-db` и `TEST_DATABASE_URL`. Браузерные тесты рассчитаны на окружение, которое создаёт `npm run qa`; для ручной проверки используйте Docker-запуск выше.

Для проверки production-образа теми же браузерными сценариями:

```sh
npm run qa -- --docker-app
```

В этом режиме скрипт дополнительно собирает `Dockerfile` и запускает приложение в контейнере. Оно подключается к той же временной тестовой БД. После проверки созданные контейнер и образ удаляются; обычные данные приложения не затрагиваются.

Для профиля Render Free с ограничениями контейнера 512 MB RAM и 0,1 CPU добавьте `--free-runtime`:

```sh
npm run qa -- --docker-app --free-runtime
```

Фактические результаты и оставшиеся проверки перечислены в [журнале проверки](docs/verification.md).

## Устройство проекта

React 19, Next.js App Router, TypeScript, Redux Toolkit, Bootstrap и CSS с именованием BEM. Backend небольшой: обработчики Next.js, параметризованные запросы MySQL, JWT и Socket.io в одном Node.js-процессе. GraphQL обслуживает запрос итогов для аналитики.

```text
src/app/          страницы, layouts, HTTP API
src/components/   общие компоненты интерфейса
src/features/     приходы, продукты, вход и аналитика
src/store/        Redux, асинхронное обновление, selectors
src/shared/       типы, схемы форм, форматирование, переводы
src/server/       MySQL, JWT, события, проверка HTTP-запросов
public/           локальные изображения, worker, service worker
database/         SQL-схема и демонстрационные записи
tests/            unit, интеграционные и браузерные тесты
scripts/          создание схемы, демоданные, полный QA
```

Детали решений — в [архитектуре](docs/architecture.md), соответствие пунктам PDF — в [матрице требований](docs/middle-requirements.md). Проверки безопасности и границы решения описаны [отдельно](docs/security.md).

## Схема БД и размещение

Файл для MySQL Workbench — [database/schema.sql](database/schema.sql). [Инструкция импорта](database/README.md) позволяет получить EER-модель из того же SQL, который создаёт таблицы приложения.

Текущий вариант размещения — постоянный Node.js-процесс либо Docker, MySQL, HTTPS и передача WebSocket-соединений через reverse proxy. Внешний адрес задаётся в `APP_ORIGIN`; proxy должен сохранять Host.

Vercel поддерживает [WebSocket и Socket.IO в public beta](https://vercel.com/changelog/websocket-support-is-now-in-public-beta). Для него нужна отдельная адаптация текущего `server.ts`: endpoint функции, внешняя MySQL и [общий счётчик и обмен событиями между инстансами](https://vercel.com/docs/functions/websockets#manage-persistent-state). Такой вариант в проекте пока не реализован.

Для бесплатного демо подготовлен `render.yaml`: Render Free для приложения и Aiven Free для MySQL с проверкой TLS. Порядок настройки, переменные и ограничения — в [инструкции размещения](docs/INFRASTRUCTURE.md). После простоя Render возможен холодный старт около минуты.

Публичное размещение для QA ещё не выполнено. Локальный адрес не заменяет ссылку на развёрнутый результат, которую требует задание.
